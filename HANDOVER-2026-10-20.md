## 1. Deploying from now on

**Automatic:** push or merge to `main`, and whm-couple builds and publishes it
in about 15 s. To change config (Supabase key, relay
servers), edit the env vars under Project configuration → Environment
variables, then Deploys → Trigger deploy. If the vars are missing, the build
fails on purpose and the previous version stays live.

**Manual fallback** (only if GitHub builds are broken), on your machine in the
repo folder:

```sh
git checkout main && git pull
ls whm-site/config.js          # must exist — it holds the Supabase URL + key
npx -y netlify-cli deploy --site bc6a3cca-6842-4ce3-9465-9aedf9fad8af --dir whm-site --prod
```

- **What's live now:** the hangout/realtime fixes **and** your Stage 3
  wise-words card (the Aug 8 upload never had it).
- **After any deploy:** reload the app on **both** devices. An open old page
  keeps running old code, and partner-rejoin detection needs both sides on the
  new build.

**Rollback if anything looks wrong:**
- To a previous *good* GitHub build: Netlify → whm-couple → Deploys → open it →
  **Publish deploy**. That's instant. (Builds from before 20 Oct on this project
  show "Setup not complete", so don't pick those.)
- To the Aug 8 version: use **whm-couple-old.netlify.app** right away, or ask
  Claude to swap the two project names back.

## 2. What was wrong, and what changed

| Problem you saw | Cause | Fix | Confidence |
|---|---|---|---|
| Screen share stops working on long calls | Supabase only refreshes the login token while the tab is **visible**. Switch to the tab you're sharing, the token expires after ~1 h, Supabase closes the hangout's signaling channel, and nothing reopened it. The call kept running peer-to-peer, but starting a share needs that channel. | Token kept fresh during the session; dropped channels rebuilt automatically; unanswered connection offers re-sent. | **Certain.** Confirmed in the pinned Supabase source and reproduced in tests; the old code fails the same tests. |
| (Probably unnoticed) chat and hearts dying at the same moment | Same channel | Same fix | **Certain** |
| (Probably unnoticed) pairing + tracker live updates stop after ~1 h in a background tab | Same token problem, all channels | New `js/realtime.js` used by **every** live connection; data is re-fetched after each reconnect, because Supabase never replays what you missed | **Certain** |
| One lost message could freeze screen share for the rest of the call | Signaling has no delivery guarantee | Offers re-sent until answered (works even if the *answer* was the lost message) | **Certain** (tested) |
| If one of you left and rejoined, the call broke unless **both** rejoined | The stayer kept a dead connection | Each session is stamped; a rejoin (or a "bye") gives the other side a fresh connection | **Certain** (tested) |
| After you'd shared once, you couldn't hear your partner's shared audio | The screen video element stayed muted | Fixed | **Certain** (tested) |
| Voice not clear | Unknown: network, earbuds, or echo | Redundant audio packets (RED), voice prioritised over video, whole-screen share no longer echoes the call, **mic picker**, **earbud warning**, mic auto-recovers if earbuds die mid-call | **Improved, not proven.** I never had your device or network details. |

Small extras fixed along the way: hearts multiplied after every rejoin; leaving
while the camera prompt was open left the camera running; the mic/camera/share
buttons kept stale labels after rejoining.

## 3. Smoke test after deploying (~10 min, two devices)

- [ ] Start a hangout on both. Within a few seconds the status line reads like
      `connected ♡ · direct · voice clear · 40 ms`.
- [ ] Share screen with "Also share tab audio" ticked: the partner sees the share
      and hears it. Stop. Then share from the **other** side: the first person
      must hear it too (this used to be silent).
- [ ] With more than one mic connected, a **mic** picker appears next to the
      buttons. With Bluetooth earbuds as the mic, a yellow hint offers the laptop
      mic. Switching mid-call doesn't drop the call.
- [ ] One person leaves and rejoins while the other stays → video comes back on
      both sides without the stayer doing anything.
- [ ] **The real test:** stay on a call **70+ minutes** with the hangout tab in the
      background part of the time, then start a screen share. It should work,
      and chat should still go through.

## 4. Reading the voice readout

The status line in the hangout now tells you which kind of problem you have:

| Readout says | Meaning | What to do |
|---|---|---|
| `direct · voice clear` but it **sounds** bad | The device, not the network | Earbuds as mic? Accept the yellow hint (laptop mic, earbuds for listening) or use wired earphones. On speakers, use headphones. |
| `direct · voice choppy · N% lost` | Your own network (weak Wi-Fi, busy line) | Move closer to the router, or turn off camera/screen share to free bandwidth. |
| `via relay · voice choppy` | Traffic goes through the shared free relay server, and it's struggling | Get your own relay: section 5, first item. |
| `via relay · voice clear` | Relay is fine | Nothing |

**Tell Claude what yours says on the next call.** It's the missing piece for the voice issue.

## 5b. Special days (anniversary fireworks)

counting from 21 Nov 2025 and 10 Dec 2025 ("happy 11 months ♡", then

  `[{"date":"2025-11-21","every":"month","timeZone":"Asia/Kolkata","title":"happy {since} ♡"}, …]`.

  Deploys → Trigger deploy.

  settings screen can replace this later.

## 7. If something breaks

- **First move:** roll back (section 1). Then open the browser console on the
  hangout page and look for lines starting with `[realtime]`, `[rtc]` or
  `[hangout]`. Paste them to Claude.
- **"Setup not complete" after deploy:** `config.js` didn't ship. Redeploy from
  the folder that has it.
- **Readout never appears:** the call never reached "connected"; check the
  `[rtc]` lines.
- **Screen share still fails on a long call:** check for
  `[realtime] hangout:…: CLOSED` followed by `rebuilding channel`. If the rebuild
  lines repeat without recovering, the token refresh is failing. Look for
  `[realtime] token refresh failed` and paste it to Claude.
